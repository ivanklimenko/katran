## Диагноз (по трём сообщениям разработчика хоста, 13.10; имена, адреса и названия репозиториев хоста сюда не переносить — репо публичный)

В обратной связи смешаны **три разные вещи**. Ошибка сборки со стилями не связана.

### 1. Ошибка `Failed to resolve entry for package "@katran/tokens"` — причина в способе публикации, не в CSS

- Что видно: хост запускает dev-сервер Vite, сканер зависимостей (`vite:dep-scan`, esbuild) падает на `import { densityOptions, type Density } from '@katran/tokens'` (в хост перенесён `Shell` из `apps/pi`): «The package may have incorrect main/module/exports».
- Как публиковали: `npm publish` из `packages/tokens` в корпоративный npm-реестр (Windows, Node 22, npm).
- Причина: манифесты пакетов рассчитаны на **`pnpm publish`**. Поля для потребителя лежат в `publishConfig` (`main`/`types`/`exports` → `dist`), а в корне манифеста — поля для монорепо (`main: ./src/index.ts`). Подмену из `publishConfig` делает только pnpm; **npm публикует манифест как есть**. В итоге в реестре `@katran/tokens` с `main: ./src/index.ts`, а в тарболе (`files`) — только `dist`, `src/tokens.css`, `src/fonts.css`. Файла входа нет → «Failed to resolve entry».
- То же ждёт остальные пакеты:
  - `@katran/effector`: `files: ["dist"]`, `main: ./src/index.ts` — упадёт так же при первом импорте.
  - `@katran/ui`: `files: ["src", "dist"]`, `main: ./src/index.ts` — потребитель получает **исходники TypeScript с CSS Modules**, а не сборку: «работает» случайно, зависит от бандлера хоста, имена классов и порядок CSS — не те, что в `dist/ui.css`.
- «Вот эта история не лечится» — лечится: это ошибка упаковки.

### 2. `workspace:*` в зависимостях — та же причина

- `pnpm publish`/`pnpm pack` переписывают `workspace:*` на конкретную версию; npm — нет. Разработчик хоста правил вручную (`"@katran/tokens": "0.1.0"` в `packages/ui/package.json` — в его клоне остались правки `M`).
- Его вопрос: «как в разработке использовать пакет из монорепы, а при публикации указывать конкретную версию» — ответ: это штатная работа `pnpm publish`; нужен один сценарий релиза, чтобы руками манифесты не трогали.

### 3. Переход на styled-components — отдельное пожелание, причина — единообразие

- Дословный смысл: «в идеале перевести библиотеку на styled-components, мы используем **5.3.11**»; «помимо этой ошибки получается дополнительная механика работы с css, что вызовет в будущем баги: часть на styled, часть на css с переменными — стилизовать придётся хаотично; у нас все реестры написаны на них».
- То есть это не «CSS не работает в хосте», а **стандарт команды и опасение двух механик стилизации в одном проекте**. **Подтверждено разработчиком хоста 13.10** (ответ на вопрос о причине: «пункт 2 — стандарт команды»: весь код хоста на styled-components, так его читают и ревьюят, отдельный способ стилизации в одном модуле не примут; цель — выглядеть как остальной код: `styled.div`, тема через `ThemeProvider`, привычные приёмы). Варианты «CSS-файлы плохо живут в федерации» и «нужна тема хоста» причиной не названы. Владелец (Иван) передал это как установку «отказаться от css и перейти на Styled Components».
- Остальное из сообщений: пакеты в корпоративный npm заехали и скачиваются; в хосте есть ветка с модулем в маршрутизации (`features/katran`), библиотеки подключены.

### Общая формула

Ошибка интеграции — из-за публикации `npm publish` вместо `pnpm publish` (манифесты с `publishConfig` и `workspace:*`). Требование styled-components — самостоятельное архитектурное пожелание хоста о единообразии; оно отменяет записанное решение проекта (STATE §2: «CSS Modules без рантайма… CSS-in-JS отвергнут»; основная спека: отказ от Admiral «снимает styled-components»).
