## 1. Зачем и что в срезе

Деталка «Платёжная инструкция» на стенде `pi-constructor` (`index.html`, около 1000 строк JS и 500 строк CSS) — последняя крупная часть стенда, не переехавшая в кит. Когда она переедет целиком (2a–2d), демо кита и `apps/pi` заменят стенд для пользователей, стенд уйдёт в архив (STATE §10).

Деталка делится на слабо связанные части, поэтому срез 2 режется на подсрезы, у каждого своя спека-дельта и свой план:

| Подсрез | Содержание |
|---|---|
| **2a** (этот документ) | Оболочка drawer со стеком A/B, шапка, лейн действий (заглушки), вкладки с переполнением, вкладка «Общие» на просмотр для валюты и рубля, порт детали и фейк |
| 2b | Остальные вкладки: Доп. поля, Статусы, Комплаенс, Связанные, Задачи, Нотификации, Исходный текст / ED244 (разбор XML), Стриминг, MPU, Аудит |
| 2c | Правка: `InlineEdit`, аудит поля (`f.hist`, таймлайн с диффом, «вторая рука»), саджест счетов Дт/Кт, 20 исх, `Prompt`, `DateInput` (дата валютирования), перезапрос реестра после действий (`refreshRequested`) |
| 2d | Остаток по сверке (настоящие действия лейна — вместе с эндпоинтами) |

### 1.1. Входит в 2a

- Открытие деталки из обоих реестров `apps/pi`: кнопка открытия — drawer A, двойной клик или Shift — drawer B рядом для сравнения; Esc закрывает верхний. Реестр остаётся рабочим: фильтры, выделение и страница не трогаются.
- Шапка: «Платёжная инструкция», `uuid` линк-кнопкой, дата создания, «×».
- Лейн действий: тег типа, статус, «название · направление», набор действий (`ACTIONS` у валюты, `ACTIONS_RUB` у рубля), «Аннулировать» за разделителем, у «Печати» — меню форм. Все действия — заглушки с `announce`, как массовые действия реестра.
- Вкладки фиксированного порядка, свои наборы у валюты и рубля (у рубля — ED244 вместо «Исходного текста» и нет «Доп. полей»); неактивные — второй группой; не поместившиеся по ширине — в меню «••• N». Содержимое в 2a — только у «Общих»; остальные — срез 2b (исполнен, спека `2026-09-30-katran-detail-tabs-design.md`).
- «Общие» на просмотр. Валюта: профили MT103 / MT202 / MT202COV / MT199 — hero, блоки (сообщения, маршрут, транзакции), сетка пар полей 50–54 | 55–59, текстовые поля, extra, у MT202COV — `seqB`. Рубль: PAYDOCRU / REQDOCRU / PAYORDRU — hero, таблица «отправитель | получатель», пять сворачиваемых секций RSECTIONS, блок транзакций. Карандашей правки нет (2c).
- Порт детали и фейковый сервер; данные вымышленные.

### 1.2. Не входит в 2a

Вкладки кроме «Общих» (2b); правка, аудит, саджест, `Prompt`, `DateInput`, перезапрос реестра после действий (2c); настоящие действия (2d, вместе с эндпоинтами); график статусов — он часть реестра, не деталки; масштаб стенда 100/110/125 % — в ките это плотность (`KatranProvider`), отдельного переключателя в деталке нет.

## 2. Заморозка и сверка

С этого момента новое поведение деталки — только через кит, на стенде — только исправления; стенд для пользователей остаётся до конца 2d.
- С эталона снимается геометрия, Chromium 1600×1000: ширина drawer, высота строки SWIFT-поля, высоты шапки, лейна действий и полосы вкладок.
- **Сверка — первая задача плана, до кода.** Новый документ `docs/reference/detail-drift.md` в формате `registry-drift.md` (классы A/B/C/D). Объём сверки 2a — части, входящие в 2a (§1.1); части 2b–2d сверяются в начале своих подсрезов против того же замороженного коммита. Пункты B — владельцу на решение; всё, что решения не требует, делается как на эталоне. Задачи кита и шва данных от решений B не зависят.
- Класс C, известный заранее: разведение клика и двойного клика делает `DataGrid` (на стенде — обработчик страницы реестра); масштаб — плотностью кита, а не CSS `zoom`; действия — заглушки.

## 3. Кит

### 3.1. `@katran/ui`

- **`Drawer`** — панель фиксированной ширины 800 (токен `drawer`; как все размеры кита, умножается на плотность — 1000 при 125 %, вопрос В-Д6 в `detail-drift.md`), прижатая к правому краю окна; не модальная: реестр под ней остаётся рабочим, как на стенде. Роль `dialog` без `aria-modal`, доступное имя — заголовок («Платёжная инструкция № …»). При открытии фокус уходит в заголовок, при закрытии возвращается туда, откуда деталку открыли (элемент передаёт вызывающий). Esc закрывает верхний drawer, кроме случаев, когда фокус в поле ввода, меню или поповере. Геометрия, тени, отступы — токенами; анимация появления короткая и отключается при `prefers-reduced-motion`. Без `inert`, `:has`, `dialog.showModal` (Chromium 88).
- **`DrawerStack`** — раскладка двух слотов: A у правого края, B слева от A; пустой слот не рендерится.
- **`Tabs`: переполнение** (основная спека §5.2). Новый проп `overflow`: порядок фиксированный; `disabled`-вкладки идут второй группой тем же порядком; вкладки, не поместившиеся по ширине, уходят в меню «••• N» (`Menu` кита), выбранная вкладка всегда видима в полосе. Клавиатура — WAI-ARIA с ручной активацией, как сейчас; пункты меню — обычные пункты `Menu`. Без `overflow` `Tabs` ведёт себя как сейчас. Добавлен и проп `variant: 'segment' | 'line'` (по умолчанию `segment`); вкладки деталки — `variant="line"` (подчёркивание выбранной). **Контракт CSS (решение контроллера R7):** вид `line` сам рисует нижнюю линию полосы тенью `inset` (под ней же кнопка «••• N»), полоса ровно 32; потребитель свою нижнюю рамку под полосой не рисует — иначе линия двойная и полоса выше.
- **`FieldRow`** — строка SWIFT-поля: тег, буква опции, значение; высота строки — эталонные 27 px (замер §2; 23 — строка таблицы сторон рубля). Пустое поле остаётся бледной строкой с прочерком (для построчного совпадения двух документов рядом), доступный текст — «не заполнено». Многострочные текстовые поля (70, 72, 79 и т. п.) — по `lines`/`width` из описания поля.
- **`ConfigForm`** — рендер формы по схеме, без знания SWIFT:

```ts
type FieldDef = { tag: string; label: string; kind: 'ref' | 'amount' | 'short' | 'party' | 'bank' | 'text'; opts?: string[] | undefined; lines?: number | undefined; width?: number | undefined }
type FieldRef = string | { tag: string; hideIfEmpty?: boolean | undefined }
type FormSchema = {
  hero?: FieldRef[] | undefined
  blocks?: string[] | undefined          // именованные слоты, рендерит приложение
  grid?: [FieldRef | null, FieldRef | null][] | undefined
  text?: FieldRef[] | undefined
  extra?: FieldRef[] | undefined
  sections?: { id: string; title: string; collapsed?: boolean | undefined }[] | undefined   // сворачиваемые, содержимое — слотом
}
type ConfigFormProps = {
  schema: FormSchema
  fields: Record<string, FieldDef>
  value: (tag: string) => { opt?: string | undefined; lines: string[] } | null
  renderBlock?: ((id: string) => ReactNode) | undefined
  renderSection?: ((id: string) => ReactNode) | undefined
}
```

  Окончательные имена и поля — по сверке (§2) и профилям стенда; принцип закреплён: схема и реестр полей — данные приложения, `ConfigForm` — механизм.

  **Уточнено по профилям стенда (план 2a, Task 5; решение контроллера R1).** Настоящие типы — `packages/ui/src/form/types.ts`:

```ts
type FieldDef = { label: string; kind: 'ref' | 'amount' | 'short' | 'party' | 'bank' | 'text'; opts?: string[] | undefined; lines?: number | undefined; width?: number | undefined; show?: number | undefined }
type FieldRef = string | { tag: string; hideIfEmpty?: boolean | undefined }   // префикс «B.» — поле последовательности B
type FieldValue = { opt?: string | undefined; acc?: string | undefined; lines: string[] }
type FormPart = { grid?: [FieldRef | null, FieldRef | null][] | undefined; text?: FieldRef[] | undefined; extra?: FieldRef[] | undefined }
type FormSection = { id: string; title: string; collapsed?: boolean | undefined }   // collapsed по умолчанию true
type FormSchema = FormPart & {
  hero?: string[] | undefined              // ключи ячеек сводки, содержимое — renderHero
  blocks?: string[] | undefined
  fieldsTitle?: string | undefined         // «Поля MT103»
  fieldsHint?: string | undefined          // «50–54 слева · 55–59 справа»
  seqB?: (FormPart & { title: string }) | undefined
  sections?: FormSection[] | undefined
  sectionsTitle?: string | undefined       // по умолчанию «Дополнительные блоки»
}
type HeroCell = { label: ReactNode; value: ReactNode; align?: 'right' | undefined; tip?: string | undefined }
type SectionContent = { body: ReactNode; count?: number | undefined } | null   // null — секция без данных
type ConfigFormProps = {
  schema: FormSchema
  fields: Record<string, FieldDef>          // ключ — тег без префикса «B.»
  value: (tag: string) => FieldValue | null
  present?: FieldPresenter | undefined      // (tag, v) => { main, second, full }; по умолчанию defaultPresent
  optionLabels?: Record<string, string> | undefined
  renderHero?: ((id: string) => HeroCell) | undefined
  renderBlock?: ((id: string) => ReactNode) | undefined
  renderSection?: ((id: string) => SectionContent) | undefined
}
```

  Отличия от эскиза выше: тег — ключ реестра полей, а не поле `FieldDef`; `FieldDef.label` — название в подсказке номера, `FieldDef.show` — сколько строк текстового поля видно до раскрытия; `FieldValue.acc` — счёт у сторон (50/59); `FormSchema.fieldsTitle`/`fieldsHint`/`seqB`/`sectionsTitle` — заголовки и последовательность B MT202COV; сводка — ключами `hero` с `renderHero`, а не полями; вид значения в строке — `present` приложения (у валюты — `swiftPresent`: главное, счёт или BIC справа, полный текст в подсказке). Кит знает префикс «B.» и `seqB` (механизм последовательности B), но не SWIFT; `kind` `'party'`/`'bank'` китом пока не используется (нужен правке, 2c), `FieldDef.width` — тоже. Высота строки SWIFT-поля — 27 (замер Task 1, токен `field-row`), 23 — строка таблицы сторон рубля (токен `party-row`).
- **`Disclosure`** — сворачиваемый блок (кнопка с `aria-expanded`, панель), для секций рубля и блока транзакций. В ките его нет — добавляется.
- **`DataGrid`**:
  - *разведение жестов открытия*: при заданном `onOpen` обычный клик по кнопке открытия откладывается на 220 мс (эталон) и отменяется вторым кликом; двойной клик даёт одно `onOpen(row, { secondary: true })`; Shift+клик — `secondary` сразу; Enter/Space с клавиатуры — без задержки. Сейчас первый клик двойного вызывает `onOpen` без `secondary`, и двойной клик по новой записи заменил бы A ею же.
  - *метка открытых записей*: новый проп `marked?: ((row: Row) => 'a' | 'b' | null) | undefined` — запись, открытая в деталке, помечается как на стенде (вид — по сверке).

### 3.2. `@katran/effector`

`createDrawerStackModel()` — стек двух слотов:

- сторы `$a`, `$b`: `{ id: string; tab: string } | null`; события `open({ id, secondary })`, `close('a' | 'b')`, `closeTop`, `setTab({ slot, tab })`;
- правила (эталон): обычное открытие заменяет A (вкладка — первая); `secondary` кладёт документ в B, а если A пуст — в A; открытие `id`, уже открытого в любом слоте, ничего не меняет и сообщает слот (для фокуса); `close('a')` при открытом B сдвигает B в A; `closeTop` закрывает B, если открыт, иначе A;
- загрузку данных модель не знает.

## 4. `apps/pi`

### 4.1. Шов данных

- `createGridPorts({ gridId, parseRow, parseDetail? })`: при `parseDetail` порты получают `detailFx: Effect<string, Detail, ApiError>` — `GET /grids/{gridId}/documents/{id}`. Ответ проверяется гардом `obj` и парсером сущности; ошибки — `ApiError` / `contractError`, как у поиска.
- Эндпоинт — **предложение** в контракт `vtb-filters`, как `/facets`; в `docs/reference/pi-api.md` — с пометкой «предложение» и составом детали для `fx-docs` и `rub-docs`.

### 4.2. Сущности (домен)

- `entities/fx-doc`: `model/detail.ts` — тип `FxDocDetail` (данные строки реестра плюс `fields: Record<тег, { opt?, lines }>`, сообщения, маршрут, транзакции; точный состав — по сверке); `model/swift.ts` — реестр полей SWIFT и профили MT103 / MT202 / MT202COV / MT199 в форме `FieldDef` / `FormSchema` (перенос `FIELDS` / `PROFILES` стенда), `schemaOf(detail)`; наборы вкладок и `ACTIONS`; `api/detail.mapper.ts` — `parseFxDocDetail` на гардах; `fxDocPorts.detailFx`; `ui/` — блоки-слоты (сообщения, маршрут, транзакции).
- `entities/rub-doc`: то же для рубля — `RubDocDetail`, профили PAYDOCRU / REQDOCRU / PAYORDRU, RSECTIONS, таблица сторон, `ACTIONS_RUB`, вкладки с ED244.
- Имена полей бека по-прежнему держат только мапперы.

### 4.3. Виджет `widgets/doc-detail`

- `createDetail({ detailFx, lifecycle })`: модель стека кита плюс загрузка по слоту — `$slots` (для каждого слота: `id`, состояние `loading | ready | error`, данные, ошибка), `retry(slot)`, кэш по `id` на время открытого экрана (переключение A↔B и повторное открытие не перезапрашивают). `lifecycle.pageClosed` закрывает оба слота и очищает кэш. Расширен в 2b: `tabFx`, `localTabs`, `tabView`, `retryTab`, `$expanded`.
- `DocDetail`: `DrawerStack` кита; в слоте — шапка, лейн действий, `Tabs` с переполнением, во вкладке «Общие» — `ConfigForm` по `schemaOf(detail)`; скелетон формы на загрузку (минимум 400 мс, как у грида), на ошибку — alert с текстом `ApiError` и «Повторить», шапка при этом показывает известное из строки реестра (номер, статус).
- Всё доменное приходит пропсами: `schemaOf`, реестр полей, вкладки, действия, `renderBlock` / `renderSection`, `describe`. `doc-detail` не импортирует `entities` — один виджет на оба реестра, как `doc-registry`.

### 4.4. Страницы и фейк

- `pages/fx-docs`, `pages/rub-docs`: модель страницы создаёт `registry` и `detail` на одном `lifecycle`; связь — `sample({ clock: registry.openRequested, target: detail.open })`. Экран рендерит `DocRegistry` и `DocDetail`; `DocRegistry` получает `marked` из модели деталки.
- Фейковый сервер: `GET /grids/{gridId}/documents/{id}` строит деталь из той же строки реестра плюс детерминированные поля по профилю (SWIFT-поля, сообщения, маршрут, транзакции; у рубля — стороны и секции). Номер, сумма и статус совпадают с реестром. Неизвестный `id` → 404; `?fail=detail` → 500. Словари — со стенда (обезличен), данные вымышленные.

## 5. Поведение

- **Открытие.** Кнопка открытия — A; двойной клик или Shift — B. Документ, уже открытый в любом слоте, повторно не открывается — фокус переходит в его drawer. Записи, открытые в A и B, помечены в реестре.
- **Закрытие.** «×» или Esc: сначала B, потом A. Фокус возвращается на кнопку открытия этой записи; если её на странице уже нет — в грид.
- **Жизненный цикл.** Уход с экрана (`pageClosed`) закрывает оба drawer'а и очищает кэш: при возврате деталки не всплывают. `refreshRequested` реестра деталь в 2a не трогает (перезапрос детали после действий — 2c). Модели статичны после импорта.
- **Ошибки.** Отказ транспорта и ответ не по контракту — состояние ошибки внутри drawer'а с «Повторить»; приложение и реестр не падают.
- **Геометрия.** Ширина drawer фиксирована при данной плотности (800 при 100 %, растёт с плотностью — при 125 % две деталки занимают 2000 px и B уходит за левый край окна уже 2000 px, открытый вопрос В-Д6, `detail-drift.md` Д29); две деталки на 1600 px закрывают грид почти целиком — как на эталоне, сознательно.
- **A11y.** Drawer — `dialog` с именем; вкладки и меню переполнения — WAI-ARIA; пустое поле озвучивается «не заполнено»; действия лейна — кнопки с доступными именами.

- **Кит.** `createDrawerStackModel` — все правила §3.2. `Drawer` / `DrawerStack` — фокус при открытии и закрытии, Esc (и его отсутствие в полях ввода), axe. `Tabs` с переполнением — группировка неактивных, хвост «••• N» (ширина в jsdom — заглушкой `ResizeObserver`, настоящая — в e2e), клавиатура. `FieldRow` — пустое и многострочное поле. `ConfigForm` — рендер по схеме, слоты, пары с `null`. `Disclosure`. `DataGrid` — разведение жестов (фейковые таймеры) и `marked`.
- **`apps/pi`.** Мапперы детали на примерах из `pi-api.md`, включая битую форму; цепочка «порт → `requestFx` → фейк» для `detailFx`: 200, 404, 500 по `?fail=detail`; `createDetail` — загрузка по слоту, кэш, повтор, `pageClosed`; `DocDetail` под axe на реальных профилях обоих реестров.

- **Совместимость.** Пакеты и `apps/pi` проходят `check:target` (Chromium 88); React 17.
